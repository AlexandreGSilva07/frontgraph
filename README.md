# Frontgraph

> **A living dependency graph embedded in your source code.**
> **Versioned architectural context for AI agents — semantic intent declared by humans, mechanical truth derived continuously from the code.**

Frontgraph turns your codebase into a queryable, self-describing dependency graph by annotating source files with `@graph` blocks. The mechanical facts (dependencies, exports) are **derived from the code itself on every parse**; the semantic facts (summary, category) are **declared by humans**. The engine detects when the two diverge (**drift**) and can rewrite the blocks back to the truth (**sync**).

This repository contains:

- **`frontgraph/`** — the reference engine: a CLI for project introspection and an MCP server so AI agents (Claude Code, Cursor, Codex) can understand your architecture in real time
- **`frontgraph/SPEC.md`** — **FRONTGRAPH-SPEC v1.0**, the normative open standard the engine implements
- **`teste/`** — a sandbox React app used as the proving ground (its business logic is irrelevant; it exists to exercise the graph)

## Core Principle

> **Derive the mechanical. Declare only the semantic.**

Most dependency graphs are external artifacts — generated by tools, stored in config files, and quickly forgotten. Frontgraph embeds the graph directly in your source code via `@graph` blocks. But a block that *only* repeats what the code already says would rot the moment the code changes.

So the spec splits every field into one of two classes:

| Class | Fields | Source of truth |
|-------|--------|-----------------|
| **Semantic** (declared) | `id`, `category`, `summary`, `doc`, `spec` | The human. The code cannot express intent. |
| **Mechanical** (derived) | `dependencies`, `exports` | The code. Re-derived from the AST on **every parse**. |

The declared `dependencies:` and `exports:` lists in a block are a **readable projection** — useful for humans reading the file, reviewed in PRs — but the engine never trusts them blindly:

- **Effective dependencies** = declared ∪ derived (the union; nothing the code imports can be hidden)
- **Effective exports** = derived (for single-block TS/JS files — the code *is* the truth); declared otherwise
- When projection and truth diverge, that's **drift** — a first-class diagnostic with four kinds, surfaced by `validate` and repaired by `sync`

This means:

- **The graph lives with the code** — it evolves as the code evolves, reviewed in PRs alongside the code
- **The graph cannot lie** — derived facts win; stale blocks are detected, not silently believed
- **AI agents can read it** — Claude Code and other AI tools query the graph to understand impact before making changes
- **No external tooling required** — the graph is parsed from the same files you already have

## The Specification

The engine is the reference implementation of **[FRONTGRAPH-SPEC v1.0](frontgraph/SPEC.md)**, a normative standard written with RFC 2119 language (MUST/SHOULD/MAY). Sections:

| § | Section | Covers |
|---|---------|--------|
| 1 | Abstract | The thesis and the derive/declare split |
| 2 | Terminology | Node, block, anchor, drift, projection |
| 3 | Block grammar | EBNF for the `@graph` block |
| 4 | Language bindings | JSDoc for TS/JS, docstrings for Python |
| 5 | Fields | Required vs optional; identity rules; categories; **§5.3 anchored nodes** |
| 6 | Derivation | **§6.1** dependencies (MUST, all languages); **§6.2** exports (MUST for TS/JS, MAY for Python in v1) |
| 7 | Drift | The four drift kinds and sync semantics |
| 8 | Graph semantics | The live-graph requirement — engines MUST reflect the current state of disk |
| 9 | Conformance levels | **L1 Reader** (parses blocks) → **L2 Deriver** (AST derivation + drift) → **L3 Live engine** (per-query re-parse) |
| 10 | Versioning | How the spec evolves |

The reference implementation in `frontgraph/` targets **L3 — Live engine**.

## How It Works

### Architecture

```
                    ┌──────────────────────┐
                    │   @graph blocks      │  ← embedded in TS/JS/Python files
                    │   in source code     │
                    └──────┬───────────────┘
                           │
                    ┌──────▼───────────────┐
                    │   parser.ts          │  ← scans files, extracts @graph blocks
                    │   parser-py.ts       │     (docstrings for Python)
                    │   GraphNode[]        │
                    └──────┬───────────────┘
                           │ calls per TS/JS file
                    ┌──────▼───────────────┐
                    │   derive.ts          │  ← TypeScript compiler API:
                    │   deriveTsFacts()    │     real imports + real exports
                    │   detectDrift()      │     declared vs derived divergence
                    └──────┬───────────────┘
                           │
                    ┌──────▼───────────────┐
                    │   graph.ts           │  ← builds dependency graph,
                    │   Graph { nodes,     │     reverse deps, BFS layers,
                    │     reverseDeps }    │     search, cycles, inference
                    └──────┬───────────────┘
                           │
              ┌────────────┼──────────────────────┬──────────────────────┬─────────────┐
              │            │                      │                      │             │
     ┌────────▼────────┐  ┌▼──────────────┐  ┌────▼──────────┐  ┌────────▼─────────┐  ┌▼──────────────────┐
     │   cli.ts        │  │  sync.ts      │  │  brief.ts     │  │  leases.ts       │  │  mcp-server.ts    │
     │   CLI (22 cmd)  │  │  block rewrite│  │  staleness.ts │  │  work-orders.ts  │  │  MCP (19 tools,   │
     └─────────────────┘  └───────────────┘  │  agent UX     │  │  coordination    │  │  live per call)   │
                                             └───────────────┘  └──────────────────┘  └───────────────────┘
```

### Data Flow

1. **Parse**: `parser.ts` walks source directories, finds `/** @graph ... */` blocks in TS/JS and Python docstrings containing `@graph`, then extracts `GraphNode` objects
2. **Derive**: for every TS/JS file, `derive.ts` parses the file with the TypeScript compiler API and extracts the *real* dependencies and exports — this happens on **every parse**, not just during retrofit
3. **Merge**: effective `dependencies` = declared ∪ derived; effective `exports` = derived (single-block TS/JS) or declared (Python, anchored files). The node also keeps `declaredDependencies`, `declaredExports`, `derivedDependencies`, `derivedExports` for drift analysis
4. **Build**: `graph.ts` constructs a bidirectional graph — forward edges (dependencies) and reverse edges (dependents)
5. **Analyze**: BFS produces dependency layers; DFS detects cycles; `detectDrift()` compares projections against truth; category matrix reveals coupling patterns
6. **Serve**: the graph is exposed via CLI commands and MCP tools. The MCP server re-parses **per tool call**, so agents always see the current state of disk (SPEC §8)

### Caching

The parser caches parsed nodes to `node_modules/.cache/frontgraph/nodes-v2.json` keyed by MD5 hashes of file contents. Subsequent runs only re-parse changed files. The cache is invalidated automatically after `scaffold`, `onboard`, `move`, and `sync` operations — and because keys are content hashes, edited files are always re-parsed (and re-derived) on the next call.

## Installation & Setup

### Prerequisites

- Node.js 18+
- A project using TypeScript, JavaScript, or Python source files

### Install the engine

```bash
cd frontgraph
npm install
```

Runtime dependencies: `@modelcontextprotocol/sdk` (MCP protocol), `zod` (input validation), and `typescript` (the compiler API used for derivation — a **runtime** dependency, not just a dev tool). Dev: `tsx`, `vitest`, `@types/node`.

### Running against a project

The CLI operates on **the directory it is invoked from** (or `FRONTGRAPH_ROOT` if set). From your project root:

```bash
# from inside your project
npx tsx ../frontgraph/src/cli.ts summary

# or from anywhere
FRONTGRAPH_ROOT=/path/to/project npx tsx /path/to/frontgraph/src/cli.ts summary

# or via the package script (runs against frontgraph/ itself unless FRONTGRAPH_ROOT is set)
cd frontgraph && npm run cli -- summary
```

### Quick Start — Existing Project

```bash
# 1. Observe what the framework sees (changes nothing)
npx tsx ../frontgraph/src/cli.ts observe --verbose

# 2. Annotate your source files with @graph blocks (uses AST derivation for deps/exports)
npx tsx ../frontgraph/src/cli.ts onboard --retrofit

# 3. Validate — references, cycles, drift
npx tsx ../frontgraph/src/cli.ts validate
```

### Configure as MCP Server (Claude Code)

Add to your project's `.mcp.json`. The server takes the **project root as its first argument** — this wins over `FRONTGRAPH_ROOT` and the cwd:

```json
{
  "mcpServers": {
    "frontgraph": {
      "type": "stdio",
      "command": "node",
      "args": [
        "--import", "tsx/esm",
        "/path/to/frontgraph/src/mcp-server.ts",
        "/path/to/your/project"
      ]
    }
  }
}
```

On Windows, pointing `command` at `frontgraph\node_modules\.bin\tsx.cmd` with absolute paths in `args` (server script, then project root) is the most robust form — see `teste/.mcp.json` for a working example.

## The @graph Block

### Format

The `@graph` block is structured metadata embedded in a source file. In TypeScript and JavaScript, use a JSDoc comment (`/** ... */`). In Python, use a docstring containing `@graph`.

A file can contain one or more `@graph` blocks. Multiple blocks are represented as separate logical nodes by using anchors in the node id (see [Anchors](#example--anchors--sub-nodes)).

```
/**
 * @graph
 * id: <unique-node-identifier>
 * category: <category-name>
 * summary: <one-line-description-of-what-this-file-does>
 * dependencies: [dep1, dep2, ...]     ← projection; derived truth wins
 * exports: [export1, export2, ...]    ← projection; derived truth wins (TS/JS)
 * doc: <path-to-documentation-file>
 * spec: <path-to-specification-file>  ← optional (SDD)
 */
```

### Fields

| Field | Required | Class | Description |
|-------|----------|-------|-------------|
| `id` | **Yes** | semantic | Unique node identifier. Convention: relative path from project root without extension. Use `#anchor` for sub-nodes. Examples: `src/logic/pricing`, `src/utils/math#formatters` |
| `summary` | **Yes** | semantic | One-line description of what this file does. Used in search results and impact analysis. |
| `category` | No (defaults to `unknown`) | semantic | The node's architectural category. Auto-discovered from directory structure or declared explicitly. Examples: `types`, `logic`, `ui`, `services` |
| `dependencies` | No | **mechanical** | Declared projection of node IDs this file depends on. Effective value is declared ∪ derived. Example: `[src/types/orders]` |
| `exports` | No | **mechanical** | Declared projection of exported symbols. For single-block TS/JS files the derived list **is** the effective value. Example: `[recalcCart, pricingPipeline]` |
| `doc` | No | semantic | Path to the documentation file for this node. Convention: `Docs/<id>.md` |
| `spec` | No | semantic | Path to the specification file (SDD). Example: `Docs/specs/orders.spec.md` |

### Conventions

- **id matches file path**: `src/logic/pricing.ts` → `id: src/logic/pricing`; anchors append `#name`. A mismatch is flagged by `validate` but the node is still returned.
- **category can be semantic**: directory discovery is informational; the `@graph` block is the authority. `src/components/OrderForm.tsx` can use `category: ui`
- **dependencies use graph ids**: `[src/types/orders]` not `['../types/orders']`
- **summary is human-readable**: "Pricing engine pipeline" not "pricing.ts"
- **default exports render as `Name (default)`**: derivation reports `export default function OrderForm()` as `OrderForm (default)`, and anonymous defaults as `default` — declare them that way (or just run `sync`)

### Example — Contract (types)

```typescript
/**
 * @graph
 * id: src/types/orders
 * category: types
 * summary: Domain type contracts — branded types, discriminated unions, Result monad, state machine
 * dependencies: []
 * exports: [OrderId, ProductId, Money, Product, Order, Result, ok, err, CATALOG]
 * doc: Docs/src/types/orders.md
 */

export type OrderId = Branded<string, 'OrderId'>
export type ProductId = Branded<string, 'ProductId'>
// ...
```

### Example — Logic

```typescript
/**
 * @graph
 * id: src/logic/pricing
 * category: logic
 * summary: Pricing engine pipeline — applies rules in priority order, recalculates cart totals
 * dependencies: [src/types/orders]
 * exports: [recalcCart, pricingPipeline, addToCart]
 * doc: Docs/src/logic/pricing.md
 */

import type { Cart, PricingRule, Result } from '../types/orders'

export function pricingPipeline(cart: Cart, rules: PricingRule[]): Result<Cart> {
  // ...
}
```

### Example — UI Component (default export)

```typescript
/**
 * @graph
 * id: src/components/OrderForm
 * category: ui
 * summary: Multi-step wizard — 4-step flow, useReducer with 16 action types, async coupon validation
 * dependencies: [src/logic/order-machine, src/logic/pricing, src/logic/validation, src/types/orders]
 * exports: [OrderForm (default)]
 * doc: Docs/src/components/OrderForm.md
 */

import { addToCart, pricingPipeline } from '../logic/pricing'

export default function OrderForm() {
  // ...
}
```

Note `exports: [OrderForm (default)]` — this is what derivation produces for a named default export. Declaring `exports: [OrderForm]` would be drift (and was, in this very sandbox, until `sync` fixed it).

### Example — Python

```python
"""
@graph
id: src/workers/reconcile
category: workers
summary: Reconciles pending orders from the processing queue
dependencies: [src/workers/client]
exports: [run]
doc: Docs/src/workers/reconcile.md
"""

from .client import fetch_pending


def run():
    return fetch_pending()
```

Python dependencies are derived from `import`/`from ... import` statements; Python exports stay **declared** in v1 (SPEC §6.2).

### Example — Anchors / Sub-Nodes

```typescript
/**
 * @graph
 * id: src/utils/math#formatters
 * category: utils
 * summary: Number formatting helpers
 * dependencies: []
 * exports: [formatCurrency]
 * doc: Docs/src/utils/math-formatters.md
 */

/**
 * @graph
 * id: src/utils/math#rounding
 * category: utils
 * summary: Rounding helpers
 * dependencies: [src/utils/math#formatters]
 * exports: [roundMoney]
 * doc: Docs/src/utils/math-rounding.md
 */

export function formatCurrency(value: number) { return value.toFixed(2) }
export function roundMoney(value: number) { return Number(formatCurrency(value)) }
```

Anchored nodes partition a file **semantically** — but derivation is file-granular, so (per SPEC §5.3):

- anchored nodes inherit the file-level derived dependencies
- their `exports:` stay **declared** (the engine cannot attribute symbols to anchors)
- they are **exempt from drift** and **never touched by `sync`**

## Derivation — TS/JS via the TypeScript AST

`derive.ts` parses each TS/JS file with the TypeScript compiler API (`ts.createSourceFile`) — no regexes — on **every parse** (SPEC §6).

### What is captured as a dependency

| Form | Example |
|------|---------|
| Static import | `import { x } from './a'` |
| Re-export | `export { x } from './a'` |
| Dynamic import | `const m = import('./a')` (anywhere in the tree) |
| CommonJS | `const a = require('./a')` (anywhere in the tree) |

### Specifier resolution (`resolveTsSpecifier`)

| Specifier | Resolution |
|-----------|-----------|
| `./x`, `../y` | Joined against the importing file's directory, normalized to posix |
| `@/utils/fmt` | Alias → `src/utils/fmt` |
| `./widgets` (directory) | → `src/widgets/index` if `index.{ts,tsx,js,jsx}` exists |
| `./orders.js` (NodeNext) | → `src/orders` if `orders.ts` exists |
| `react`, `zod` (bare packages) | **Dropped** — external, not a graph node |
| `./app.css`, missing files | **Dropped** — only specifiers that resolve to a real `.ts/.tsx/.js/.jsx` on disk become dependencies |
| `../../outside-the-root` | **Dropped** — escapes above the project root resolve to `null` |

### What is captured as an export

| Form | Derived as |
|------|-----------|
| `export const a = 1` / `let` / `var` | `a` (binding patterns recursed: `export const { p, q } = ...` → `p`, `q`) |
| `export function fn() {}` / `export class K {}` | `fn`, `K` |
| `export interface I {}` / `type T` / `enum E` / `namespace N` | `I`, `T`, `E`, `N` |
| `export default function main() {}` | `main (default)` |
| `export default 42` / `export = x` | `default` |
| `export { x as y }` | `y` |
| `export { helper } from './helper'` | `helper` (and `./helper` becomes a dependency) |
| `export * from './a'` | dependency captured; symbols **not enumerated** in v1 (SPEC §6.2) |

The derived facts are attached to every node as `derivedDependencies` / `derivedExports`, alongside the original `declaredDependencies` / `declaredExports`.

## Drift Detection

**Drift** is a divergence between a block's declared projection and the code's derived truth (SPEC §7). `detectDrift()` runs on every CLI/MCP invocation and reports four kinds:

| Kind | Meaning | Example message |
|------|---------|-----------------|
| `undeclared-dependency` | Code imports something the block omits | `code imports 'src/logic/pricing' but the @graph block does not declare it` |
| `stale-dependency` | Block declares a dep the code no longer imports | `block declares dependency 'src/old' but the code does not import it` |
| `undeclared-export` | Code exports a symbol the block omits | `code exports 'App (default)' but the @graph block does not declare it` |
| `stale-export` | Block declares an export the code no longer has | `block declares export 'App' but the code does not export it` |

### Rules that keep the signal clean

- **Externals are never flagged**: `stale-dependency` only fires when the declared dep is an internal graph node — declaring `react` in `dependencies:` is allowed and ignored
- **Anchored declarations are satisfied by the base file**: declaring `src/utils/math#formatters` is satisfied by a derived dependency on `src/utils/math`
- **Anchored nodes are skipped entirely** — drift is undefined for them
- **Nodes without derived facts** (e.g., Python exports) report nothing for that dimension

### Severity

Drift is a **warning by default** — `validate` prints it but still exits 0. To make drift fail the build, enable the architecture rule:

```json
{
  "architectureRules": {
    "strict_drift": true
  }
}
```

Example `validate` output with drift present (non-strict):

```
$ npx tsx ../frontgraph/src/cli.ts validate

All checks passed
  7 nodes parsed across 1 source root(s)
  All dependency references resolve

Drift between declared blocks and derived truth (2):
  ⚠ src/App: code exports 'App (default)' but the @graph block does not declare it [undeclared-export]
  ⚠ src/App: block declares export 'App' but the code does not export it [stale-export]

  Run 'frontgraph sync' to rewrite blocks with the derived truth.
```

With `strict_drift: true` the markers become `✗`, the run prints `Drift (strict_drift enabled — failing)`, and the exit code is 1.

## The sync Command

`sync` repairs drift by rewriting the declared lists with the derived truth — the projection is regenerated, never the other way around.

```
$ npx tsx ../frontgraph/src/cli.ts sync

Syncing @graph blocks with derived truth...

Updated (3):
  ~ src/App.tsx
  ~ src/components/OrderForm.tsx
  ~ src/main.tsx

4 file(s) already in sync.
```

Guarantees:

- **Only `dependencies:` and `exports:` are rewritten** — `summary`, `category`, `doc`, `spec` are never altered
- **Dependencies are written sorted** for stable diffs
- **Anchored / multi-block files are never touched** (reported under `Skipped anchored files`)
- **Python**: dependencies are synced (they are derived), exports are left as declared (SPEC §6.2 — MAY in v1)
- The parse cache is invalidated before and after, so the next query sees the rewritten blocks

The same operation is available to agents as the MCP tool `graph_sync`.

## Semantic Staleness

Drift detection keeps the **mechanical** layer honest — but nothing in an AST can tell you that a `summary` written for a 50-line file no longer describes the 500-line file it became. That is **semantic staleness**, and it is mechanically undetectable. The engine flags it with a heuristic instead (`src/staleness.ts`):

- A content ledger (`node_modules/.cache/frontgraph/staleness-v1.json`) records, per annotated file, the hash of its `@graph` block(s) and a **baseline of the body** taken the last time the block changed
- On every `validate` / `brief`, the engine compares: if the **body keeps changing while the block stays untouched**, the block becomes suspect

| Signal | Threshold |
|--------|-----------|
| Body churn | ≥ 3 observed body changes without a block edit |
| Body growth | body line count drifted ≥ 50% from the baseline (files ≥ 10 lines) |

Output in `validate` (and the MCP `graph_validate`):

```
Summary staleness suspects (1) — informational, never fails the build:
  ? src/logic/pricing: body changed 4x since the @graph block was last touched

  The code moved since these blocks were written — review the summaries.
```

Properties:

- **Informational only** — staleness never fails a build and never counts toward the validate total. It is a review prompt, not a rule.
- **Self-resetting** — any edit to the `@graph` block (e.g., refreshing the summary) resets the baseline
- **Best-effort** — the ledger lives in `node_modules/.cache`; losing it only resets the heuristic
- **Sharpens with use** — churn counts observed transitions, so every `validate`/`brief` run is an observation

Suspect nodes are also marked `⚠ summary may be stale` inside `graph_brief` output — so an agent consuming a briefing knows which summaries to double-check before trusting them.

## Agent Briefing — graph_brief

The first **native consumer** of the graph: a token-budgeted architectural digest for an agent (or human) arriving cold at the repository. Instead of burning context exploring, the agent calls one tool and receives the most valuable facts that fit the budget.

```bash
# CLI
npx tsx ../frontgraph/src/cli.ts brief --tokens 800
```

```
# Architectural brief: complex-order-app
7 graph nodes across source root(s): src
Methodologies observed: CDD (contracts in src/types)
Categories: logic(3), entry(2), contract(1), ui(1)

## Architecture
Dependency flow: contract → logic → ui → entry
Layers (foundation → entry): L0: 1 [contract]  L1: 3 [logic]  L2: 1 [ui]  L3: 1 [entry]  L4: 1 [entry]
Foundation nodes (everything builds on these): src/types/orders

## Health
Drift: none — @graph blocks match the code

## Key nodes (by connectivity, 7 total)
- src/types/orders [contract] — 4 dependent(s), 0 dep(s)
  Domain type contracts — branded types, 4 discriminated unions, Result monad, ...
- src/components/OrderForm [ui] — 1 dependent(s), 4 dep(s)
  Multi-step wizard component — 4-step flow, 16 action types via useReducer, ...
...

Next: graph_search to locate code, graph_dependents before editing, graph_validate after.
```

### How the budget is spent

Content is emitted in priority order until the budget (`chars/4` estimate, hard ceiling) runs out:

1. **Identity** — project name, node count, source roots, methodologies, category histogram
2. **Architecture** — dependency flow, compact layer map, foundation nodes
3. **Health** — drift count, cycles, parse errors, staleness suspects
4. **Key nodes** — ranked by connectivity (`dependents × 3 + deps`), each with its summary; stale-suspect nodes carry a `⚠ summary may be stale` marker

**Truncation is always explicit.** If the budget can't hold every node, the brief says so:

```
(1 of 7 nodes shown — raise budget_tokens for more, or use graph_search / graph_deps for specifics)
```

A brief that silently omitted nodes would read as complete — that's worse than no brief.

### Via MCP

The `graph_brief` tool takes `budget_tokens` (200–32000, default 2000). Its description instructs agents to call it **first** when starting work on an unfamiliar codebase, then drill down with `graph_search` / `graph_deps`. The output is deterministic for the same project state.

This is the "context transfer" payoff of the whole system: the declared semantic layer (summaries), the derived mechanical layer (real topology), and the health diagnostics (drift, staleness) compressed into one artifact an agent can consume in a single tool call.

## Multi-Agent Coordination

One agent needs legibility; a **swarm** needs coordination. The graph already knows the two facts that make concurrent work safe — which subgraphs overlap, and what order a breaking change must propagate in. Phase 3 turns those into primitives (full protocol: [`frontgraph/COORDINATION.md`](frontgraph/COORDINATION.md), non-normative, SPEC v2 candidate).

Coordination state lives in **`.frontgraph/`** at the project root (gitignore it) — every read-modify-write happens under an exclusive directory lock, so concurrent MCP server processes cannot interleave updates.

### Leases — exclusive intent over subgraphs

An agent **claims** nodes before editing them. Another agent claiming an overlapping set is rejected — with the holder, intent, overlap, and expiry, so it can decide: wait, negotiate, or work elsewhere.

```
$ frontgraph claim src/types/orders --holder agent-alice --intent "breaking change in Money" --impact

Lease L1 granted to 'agent-alice' until 2026-06-11T00:32:13Z
  scope: impact — 7 node(s) claimed:
  ⛔ src/App
  ⛔ src/components/OrderForm
  ⛔ src/logic/order-machine
  ...

$ frontgraph claim src/components/OrderForm --holder agent-bob --intent "adjust wizard"

Claim REJECTED — conflicts with 1 active lease(s):
  ✗ L1 held by 'agent-alice' (breaking change in Money) — overlap: src/components/OrderForm
```

| Property | Behavior |
|----------|----------|
| **Scope `nodes`** | Claims exactly the listed ids |
| **Scope `impact`** | Claims the ids **plus all transitive dependents** — the right scope for contract changes |
| **TTL** (default 30 min) | Leases expire on their own; a crashed agent cannot block the graph forever |
| **Self-overlap** | A holder may widen their own claim without self-deadlock |
| **Advisory** | The engine can't stop a rogue process from editing files — leases are the contract between cooperating agents, made visible in `graph_brief`, `graph_leases` |

### Work orders — contract-diff plans with gated execution

`plan <id> <change>` converts a planned change into a **work-order DAG** over the transitive dependents, wired bottom-up:

```
$ frontgraph plan src/types/orders "rename Money to Currency"

Plan P1 — 7 work order(s):
  WO1 → src/types/orders (READY)
  WO2 → src/components/OrderForm (blocked by WO1, WO3, WO4, WO5)   ← diamond join: waits for ALL siblings
  WO3 → src/logic/order-machine (blocked by WO1)
  WO4 → src/logic/pricing (blocked by WO1)
  WO5 → src/logic/validation (blocked by WO1)
  WO6 → src/App (blocked by WO2)
  WO7 → src/main (blocked by WO6)
```

The DAG is **enforced**, not advisory: an order cannot leave `pending` while any blocker is unfinished —

```
$ frontgraph orders start WO2
✗ 'WO2' is blocked — upstream order(s) not done yet
  blocked by WO1 (src/types/orders) — pending
  ...
```

`ready` orders (pending, all blockers done) are the **frontier** a swarm picks parallel work from. The loop per agent: pick a ready order → `claim` its node → `start` → edit → validate/sync → `done` → `release` → repeat.

### Visibility

Arriving agents see coordination state where they already look — the brief's Health section:

```
Active leases: 1 — these nodes are claimed by other agents:
  ⛔ 'agent-alice' holds 7 node(s) (src/App, src/components/OrderForm, …) — breaking change in Money
Open work orders: 6 (3 ready to start) — see graph_work_orders
```

## MCP Server & Tools

**The graph is live (SPEC §8)**: every tool call re-loads project state from disk — config, nodes, derivation, drift — backed by the MD5 content cache so unchanged files are not re-parsed. An agent that edits a file and immediately queries the graph sees the new topology. There is no stale snapshot.

## Categories & Discovery

### How Categories Work

Categories are **discovered from your directory structure**, not hardcoded. Each top-level subdirectory under a source root becomes a category.

```
src/
  types/        → category: "types"
  logic/        → category: "logic"
  components/   → category: "components"
  services/     → category: "services"
  App.tsx       → category: "root"  (files directly in src/)
```

The `@graph` block's `category:` field does not have to match the directory name. Directory discovery is used for observation and onboarding suggestions; the `@graph` block is the authority for existing nodes. If `category:` is omitted, the node gets `unknown`.

## Methodologies

The framework observes three development methodologies from what exists on disk. There are no on/off toggles — if the artifacts exist, the methodology is active.

### CDD — Contract-Driven Development

**Observed when**: Directories named `types`, `interfaces`, `contracts`, `schemas`, `models`, or `dto` contain supported source files.

**Effect**: `workflow` and `scaffold` commands include a contract step. `gate` checks for contract existence before implementation.

### TDD — Test-Driven Development

**Observed when**: `*.test.*` / `*.spec.*` files or `__tests__/` directories exist. Framework (vitest, jest, mocha) is detected from `package.json`.

**Effect**: `workflow` and `scaffold` include a test step. `coverage` command becomes active.

### SDD — Specification-Driven Development

**Observed when**: `*.spec.md` files exist in `Docs/specs/`, `specs/`, `docs/specs/`, or `specifications/`.

**Effect**: `workflow` includes a spec step. `gate` checks for spec existence. `onboard --specs` creates spec stubs.

### Multiple Methodologies

All three can be active simultaneously. The workflow adapts:

```
SDD → Write specification
CDD → Define contract
TDD → Write tests
(always) → Implement logic
(always) → Write documentation
(always) → Add @graph blocks
```

## Architecture Inference

The framework **infers** architecture from the graph's topology rather than enforcing predefined rules.

| Concept | How It's Computed |
|---------|-------------------|
| **Foundation layer** | Nodes with zero internal dependencies (Layer 0 in BFS) |
| **Natural flow** | Categories ordered by average layer depth |
| **Dependency matrix** | `{fromCategory: {toCategory: count}}` for all category pairs |
| **Leaf nodes** | Nodes nothing depends on |
| **Observed patterns** | Human-readable sentences describing the architecture |

Because effective dependencies include the derived truth, the inference reflects what the code **actually does**, not what the blocks claim.

### User-Defined Architecture Rules

Optional. Add to `graph.config.json` if you want enforcement:

```json
{
  "architectureRules": {
    "no_circular_deps": true,
    "no_ui_in_logic_deps": true,
    "contract_at_layer_zero": true,
    "enforce_doc_for_all_nodes": false,
    "strict_drift": true
  }
}
```

Without user-defined rules, `validate` only checks universal properties (broken references, missing docs, parse errors, cycles) and reports drift as warnings.

## Onboarding Protocol

The onboarding protocol integrates the framework into a project. It is **non-destructive** — it annotates existing files but never moves them or creates unwanted directories.

### Phases

```
Phase 1 — Observation:  Scan project, discover categories, observe methodologies
Phase 2 — Annotation:   Add @graph blocks to unannotated source files
Phase 3 — Spec stubs:   Create spec stubs if SDD observed (optional)
Phase 4 — Validation:   Parse and validate the annotated project
```

### What Retrofit Does

For each supported source file (`.ts`, `.tsx`, `.js`, `.jsx`, `.py`) without a `@graph` block:

1. **Infers category** from the file's directory (e.g., `src/services/payment.ts` → `category: services`)
2. **Derives dependencies and exports via the AST** — retrofit calls the same `deriveTsFacts()` the live engine uses, so the generated blocks start drift-free
3. **Generates doc path**: `Docs/<id>.md`
4. **Prepends** the `@graph` block to the file
5. **Creates** a doc stub at the doc path

Files that already have `@graph` blocks are **skipped** — never overwritten.

```typescript
import { parseProjectWithErrors } from 'frontgraph/parser'
import { buildGraph, depthOrder, detectCycles, inferArchitecture } from 'frontgraph/graph'

const root = process.cwd()
const { nodes, errors } = parseProjectWithErrors(root)

const drift = detectDrift(nodes)

console.log(`Nodes: ${nodes.length}, layers: ${depthOrder(graph).length}`)

if (drift.length > 0) {
  const result = syncGraphBlocks(root)
  console.log(`Synced: ${result.updated.join(', ')}`)
}
```

```typescript
interface GraphNode {
  id: string
  category: string
  summary: string
  dependencies: string[]            // effective: declared ∪ derived
  exports: string[]                 // effective: derived (single-block TS/JS) or declared
  doc: string
  filePath: string
  spec?: string
  declaredDependencies?: string[]   // the projection as written in the block
  declaredExports?: string[]
  derivedDependencies?: string[]    // the truth from the AST
  derivedExports?: string[]
}
```

## FAQ

### Do I need graph.config.json?

**No.** The framework works entirely from auto-discovery. The config file is only for overrides, metadata (descriptions/colors), and architecture rules like `strict_drift`.

### Do I have to maintain the dependencies/exports lists by hand?

**No — and you shouldn't.** They are derived from the AST on every parse; the lists in the block are a readable projection. Write code, run `frontgraph sync` (or let your agent call `graph_sync`), and the projection is regenerated. Hand-editing them only creates drift warnings.

### What happens if the block and the code disagree?

The engine believes the code. Effective dependencies are declared ∪ derived (nothing can be hidden); effective exports for single-block TS/JS files are the derived list. The disagreement is reported as drift — a warning by default, a `validate` failure under `strict_drift`.

### Can the summary lie too?

Yes — and no AST can catch it, because summaries express intent. The engine flags it heuristically instead: if a file's body keeps changing while its `@graph` block stays untouched, the block becomes a **staleness suspect** (see [Semantic Staleness](#semantic-staleness)). It's informational only — a prompt to re-read the summary, never a build failure.

### How does an agent get oriented in a repo it has never seen?

One call: `graph_brief(budget_tokens)`. It returns the architecture, health, active leases, and most-connected nodes with their summaries, compressed into the requested token budget with explicit truncation. From there the agent drills down with `graph_search`, `graph_deps`, and `graph_impact`.

### How do multiple agents avoid stepping on each other?

Two primitives (see [Multi-Agent Coordination](#multi-agent-coordination)): **leases** — claim nodes before editing (`graph_claim`, with `impact` scope for contract changes); overlapping claims are rejected with the holder and intent, and TTLs guarantee a crashed agent's claim dissolves; and **work orders** — `graph_plan` turns a breaking change into a bottom-up DAG whose execution is gated: no order starts before everything it imports from the affected set is adapted. Coordination state lives in `.frontgraph/` (gitignore it), lock-protected against concurrent server processes.

### Can a rogue agent ignore the leases?

Yes — leases are advisory: the engine cannot stop a process from writing files. They are the contract between *cooperating* agents, made impossible to miss (`graph_brief` shows active claims on arrival). Enforcement hooks (e.g., a pre-edit check) are an integration concern, not an engine one.

### Why can I still declare dependencies at all?

Two reasons: (1) anchored nodes and Python exports have no derivation, so declaration is their only channel; (2) you may declare *conceptual* dependencies (e.g., on an anchored sub-node like `src/utils/math#formatters`) that derivation can only see at file granularity — the drift checker treats a derived dep on the base file as satisfying the anchored declaration.

### Does this work with JavaScript?

Yes. `.js`/`.jsx` files get the same per-parse AST derivation as TypeScript, including CommonJS `require()` calls and `module.exports` patterns at retrofit time.

### Does this work with Python, Go, Rust?

Python is supported: docstring `@graph` blocks, dependencies derived from `import X` / `from X import Y` when they resolve to project-local `.py` files; exports remain declared in v1 (SPEC §6.2 — MAY). Go and Rust are not supported yet, but the graph engine and the spec are language-agnostic — a new binding needs a block extractor and (for L2+) a deriver.

### Can I have multiple @graph blocks in one file?

Yes — anchored nodes (`src/utils/math#formatters`, `src/utils/math#rounding`). Each anchor is a distinct logical node sharing one physical file. Per SPEC §5.3, anchored nodes inherit file-level derived dependencies, keep their declared exports, are exempt from drift, and are never rewritten by `sync`.

### What happens if I move a file?

Use `move <source> <destination>`. It updates the moved file's node id, dependent graph references, matching doc paths, the cache, and local JS/TS import or `require()` specifiers. Run `validate` after; Python import statements may still need a manual review.

### How is this different from Madge, dependency-cruiser, etc.?

Those tools generate dependency graphs as **external artifacts** from import analysis. Frontgraph embeds the graph **in the source code** as `@graph` blocks, and:

- The graph is version-controlled alongside the code and reviewed in PRs
- AI agents query it live via MCP — every call reflects the current disk state
- It captures developer intent (summary, category, doc, spec) **and** mechanical truth (AST-derived deps/exports), and tells you when they diverge
- It integrates methodologies (CDD/TDD/SDD) into the workflow
- It is backed by an open spec (FRONTGRAPH-SPEC v1) with defined conformance levels

### What's the performance impact?

The parser runs per invocation (CLI) or per tool call (MCP), backed by the MD5 content cache — only changed files are re-parsed and re-derived. A project with 500 files parses in under 2 seconds cold, and cached runs are dominated by hashing, typically well under 100ms.

### Is the MCP graph ever stale?

No. The server reloads project state on **every** tool call (SPEC §8 — live graph). This was a deliberate fix: earlier versions parsed once at startup and served a frozen snapshot, which is poison for agents that edit files mid-session.

## Contributing

The framework is designed to be extended:

- **Add language support**: implement a block extractor (L1) and a deriver (L2) for Go comments, Rust attributes, or other language-native metadata — see SPEC §4 and §6
- **Add methodology**: extend `observeMethodologies()` with new detection patterns
- **Add architecture rule**: add new checks to `validateReferences()` or the user-defined rules system
- **Add MCP tool**: register a new tool in `mcp-server.ts` following the existing `withState` pattern

The core principle: **the graph emerges from the code, not from configuration — derive the mechanical, declare only the semantic.**
